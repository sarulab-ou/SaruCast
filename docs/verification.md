# 検証結果 — SaruCast 0.1.2 / Cast Streaming

2026-11-06（日本時間）。配布物は **SaruCast-win-x64.zip**。ZIP全体を展開し、最上位の **SaruCast.exe**を起動する。SelfContained=true、win-x64、PublishSingleFile=false。

## 環境と判定の区別

Windows 11 Education x64（10.0.26200）、Intel Core Ultra 7 255H（論理16CPU）、Intel Arc 140T（ドライバー32.0.101.6452）、1920×1280の単一モニター、Wi-Fi IPv4。テレビ名は「オフィス」。メーカー・機種は未確認。SDK 10.0.403、ランタイム10.0.14、FFmpeg 9.0.2、NAudio 2.2.1、Concentus 2.2.2。

自動検証、テレビの受信完了通知、利用者による表示・聴取を別々に記録する。診断JSONのtelevisionObservedPlaybackVerified=falseは、プログラム自身が画面と音を物理的に観測していないことを示す。以下の実際の表示・音声は、このセッションでの利用者報告に基づく。

音声フレーム数は20ms単位。音声OFFの接続のために無音AACを付け足す旧HLS経路は使っていない。テスト音のaudioPeakPcm16=0はWASAPIを使用していないためで、合成音が無音という意味ではない。合成Opusは自動テストで復号し、テレビの音は利用者が別に確認した。

## ZIP展開後の確認

0.1.2のZIPを空白入りの新しいフォルダーへ全展開し、434ファイルのハッシュが一致した。PATHをWindows標準ディレクトリに絞り、DOTNET_ROOT／DOTNET_ROOT_X64を存在しない場所にしても、同梱ランタイム10.0.14で起動し、画面列挙と標準15fpsを確認できた。GPUとソフトウェアの同梱H.264エンコーダーは、各4秒のテスト模様から60フレームを生成・復号した。復号画像の平均輝度の最小値もGPU 123.162／ソフトウェア123.180で、全面黒ではなかった。別のクリーンなPCでの試験とは区別する。

## 測定値

| 条件 | 受信確認まで | 送信・CPU |
|---|---|---|
| 実画面720p上限・15fps・音声オフ、90秒 | 1.63秒 | 1358映像フレーム |
| 最終設定のテスト模様720p上限・15fps＋Opus、120秒 | 診断JSONに記録 | 映像1812、音声6033。FFmpeg平均0.49%、SaruCast平均0.56% |
| 実画面1620×1080・15fps＋WASAPI/Opus、1800秒 | 1.89秒 | 実測15.00fps、映像27009、音声90058、映像再送64packet。FFmpeg平均5.89%、SaruCast平均0.30% |

計測はCLI診断で行い、GUIの表示負荷は含まない。再送数は映像streamのもので、音声の再送数は集計していない。CPUは区間CPU時間差を経過時間と16論理CPUで割った全体比率。目標ビットレートは15fpsで1080pが4Mbps、720pが2Mbps、Opusが128kbps。実際のビットレートは映像内容・エンコーダーで変わる。

開始から受信確認までの時間と、テレビ表示までの遅延は異なる。targetDelay=200msや受信checkpointを表示遅延として報告しない。利用者が許容範囲とした体感は確認済みだが、PCとテレビの同一カウンターを同時撮影した秒数の実測は未実施。約1秒という設計目標の達成は未判定。

## メモリの推移と長時間試験の範囲

30分試験の10秒間隔のWorking Setは、FFmpegが最初のサンプル240.0MB→終了時316.7MB（最大318.3MB）、SaruCastが74.7MB→87.3MB（最大92.4MB）。最初のサンプルは配信開始後約10秒で、プロセス起動直後の値ではない。FFmpegには中盤の段階的な増加があり、原因は未特定。キャッシュの増加かリークかはこの測定だけで判定せず、長期のメモリ安定性は残課題とする。

長時間試験は候補版のCLIで実施。最終版のUIスレッド分離・停止は自動回帰と短時間の実機再接続で確認する。GUIを実際に操作しながら30分間使った試験とは区別する。テレビでの長時間の音ずれを同時撮影・録音して測ってはいない。

## 未検証・制限

- 開発ツール・ランタイムを一度も入れていない別のクリーンなWindows 11 x64での起動。
- テレビの映像と音の時間差の実測。単なる送信継続や受信通知の進み方だけでは、長時間の音ずれを保証しない。
- Chrome完全終了時、GPUアクセラレーションONのスクロール・非保護動画について個別のテレビ表示試験。
- 複数モニター・複数NIC・VPN／有線併用・別機種テレビ。現在は各1系統での実績。
- TV電源OFF、ネットワーク断、スリープ復帰、音声出力変更の最終GUI網羅試験。検出と停止処理は実装済み。
- device-auth証明書検証、WGC、HDR変換、個別ウィンドウ共有、高度な適応帯域制御、Authenticode署名。

生の診断JSONとログは開発フォルダーartifacts/へ保存し、配布ZIPへ混ぜない。下記は削除済みのHLS経路の履歴であり、現行Cast Streamingの検証結果へ流用しない。

## 修正内容

- Cast接続後のIPv6マップ形式アドレスでHTTP bindを失敗する経路を、IPv4ソケットの明示で修正。
- HLS送信値を音声ts・映像mpeg2_tsへ修正。Receiverの初期IDLEを終了と区別し、要求したコンテンツだけを追跡。
- 初期セグメントと保持数を増やして開始位置を明示。DXGIの取得時刻とPCMサンプル時刻を、読み取り時刻で上書きする方式を除去。
- Closingイベント内での再Closeを非同期化。停止の完了を共有し、一部の後始末に失敗しても残りの資源を解放。
- 手入力IPの保存・復元、検索と接続確認の競合、古い接続からの状態上書きを修正。

## 未検証・未達

- 開発ツール・ランタイムを一度も入れていない別のクリーンなWindows 11 x64での起動。
- 30分の実機連続配信、音ずれの実測、長期メモリ増加、PCとテレビのカウンター同時撮影による表示遅延。
- Chrome完全終了時と、GPUアクセラレーションONのスクロール・非保護動画について、テレビ表示を個別に確認する受け入れ試験。
- 音声OFF、開始キャンセル、再接続、TV電源OFF、スリープ復帰、音声出力先変更を含む最終GUIの網羅的な実機操作。
- 複数モニター、複数NIC、VPN、有線併用、別機種テレビ。今回の検証は各1系統。
- WGC、HDR変換、個別ウィンドウ共有、直接Cast Streaming、1秒未満の表示遅延。
- Cast device-auth証明書検証。自己署名TLSを許容するため、信頼できるLANで使うテスト版。
- Authenticode署名。使用可能な証明書を確認できず未署名。

生の診断結果は開発フォルダーartifacts/のJSON・ログに保存。LANアドレスやセッションURLを含む診断データは配布ZIPに追加しない。
